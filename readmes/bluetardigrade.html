bluetardigrade

A self-hosted SOC for Windows endpoints: detect, investigate and respond from one console.

Rust ETW sensor · single-binary Go detection engine · live web console.
Named after the most resilient animal on Earth.

Watch the demo · Quickstart · Features · Console tour · On your phone · Notifications · Security · Architecture · Docs · Guía en español

▶  Full tour in video (MP4, 2 min 12 s)

A sensor on each Windows machine streams process, network, DNS, registry and file telemetry to a single static Go engine. The engine matches it against readable YAML rules mapped to MITRE ATT&CK, correlates kill chains, scores host risk and freezes a forensic bundle for every alert. Analysts triage, investigate and respond from a live web console, in Spanish or English, dark or light.

[!NOTE] Pre-1.0 (v1.0.0-rc1): built for labs, research and small SOC teams. Product builds contain no demo telemetry generator: an empty or disconnected console stays empty. The clips and screenshots below use the repository's contract-true fixtures (LAB-* hosts), and the console labels that window as demo data.

See it in action

Every clip is a real run of the console, driven by a script you can replay (record_demo.mjs). The interface shown is the Spanish one; a toggle in the header switches it to English.

1 · Sign in

Local accounts with roles (viewer, analyst, administrator), Active Directory accounts whose groups grant the role, optional or per-role two-step sign-in (TOTP + recovery codes) and secure sessions. Every attempt lands in the audit trail.

2 · Triage the alert queue

The panel says what needs attention now. The queue filters by severity, lifecycle and owner; each alert opens its detail, entity graph and forensic bundle; several alerts can be acknowledged, closed, assigned, suppressed or added to an incident in one go.

3 · Work an incident

Incidents group alerts across machines, with status, severity, owner, summary, an incident graph and a timeline of every change and note — exportable as Markdown or a printable report.

4 · Know every host

The fleet at a glance (online, silent, idle) from sensor heartbeats, guided enrollment of new machines, and a page per host: risk, sensor health, the live process tree, entity graph, timeline and network destinations.

5 · Engineer detections

Rule coverage by ATT&CK tactic, severity and event type; kill chains drawn as flows with per-step alerts; suppressions with a reason and an expiry; and a rule tester that dry-runs an event against the live rules.

6 · Watch telemetry and platform health

The live feed with pause, search, type filters and JSONL/CSV export, and the health of every stage: engine, ingest, queues, store and external delivery. Metrics the engine does not publish show —, never a fake zero.

7 · Respond, on your terms

Active response is off until you arm it, needs per-operator credentials, refuses protected processes, and every attempt — executed or denied — is audited.

8 · Move fast: keyboard, themes and NOC mode

Ctrl+K reaches any view or action, g + a letter jumps between views, deep links survive a refresh, and NOC mode turns a wall monitor into a rotating situation board.

9 · Get alerts by mail, chat and on your phone

Email, Telegram, Slack and ntfy push channels, each with its minimum severity, edited in Ajustes → Avisos externos and applied without restarting the engine. Enviar prueba asks each channel to answer, and every message links to its alert. More below.

10 · On call from your phone

/movil is the console built for a phone, and it installs as an app:

  • the open alerts at or above a severity, with Reconocer and Cerrar on each card;
  • the open incidents, most severe first;
  • the machines, the silent ones first;
  • one tap opens the same record in the full console.

Same sign-in, same roles, same audit trail as the desktop. How to connect it.

Why bluetardigrade

🧱 One binary, no runtime dependencies
The engine is a static Go executable: ingest, detection, correlation, API, SQLite history and delivery in one process.

📖 Detections you can read
Every rule is YAML mapped to MITRE ATT&CK, hot-reloaded and testable from the console. Sigma rules can be imported. Nothing is a black box.

🧾 From alert to evidence
Every alert freezes a forensic bundle: the triggering event plus a five-minute timeline of the host, with its process tree.

🔒 Safe by default
Loopback-only listeners, authenticated ingest, append-only evidence, audited access and active response that stays off until you arm it.

What you get

🎯 Detect

  • 125 YAML rules across 13 of the 14 ATT&CK tactics: initial access, LOLBAS, privilege escalation, credential access, lateral movement, collection, exfiltration, ransomware, hack tools, phishing and Active Directory attacks (DCSync, Kerberoasting, privileged groups).
  • 13 kill-chain correlations: 11 within a host, 2 that follow one account across machines.
  • YARA in the sensor: written files, on demand and process memory, with a rule pack the engine distributes.
  • Offline threat-intel lists, per-host process baseline, C2 beaconing, volumetric thresholds and decaying risk scores.
  • Sigma import and 17 rule operators.

🔎 Investigate

  • Live console with 13 views, command palette, deep links and ES/EN.
  • Forensic bundles with JSON/JSONL export.
  • Paged history backed by SQLite, plus a read-only SQL view for administrators.
  • Alert lifecycle, assignment, notes and saved searches.
  • Incidents with graph, timeline and Markdown or printable reports.
  • Active Directory directory and posture, read-only.
  • A phone view that installs as an app (/movil).
  • Optional AI analyst with your own model.

⚡ Respond

  • Opt-in kill_process, armed per engine.
  • Per-operator credentials: every action has an owner.
  • Every request, executed or denied, in a forensic audit log.
  • Host groups limit what each account sees and touches.

🔌 Integrate

  • Webhooks, Elasticsearch, Splunk HEC, Slack, Telegram, email and ntfy phone push, the channels edited from the console.
  • REST + SSE API with an OpenAPI contract checked in CI; Prometheus metrics.
  • Imports Suricata, Zeek, osquery, Cowrie, Windows firewall logs, offline EML mail and DC Security logs over WEF.

Quickstart

[!IMPORTANT] Use a normal PowerShell to install and run, and an Administrator PowerShell only when a step says so (kernel ETW tracing needs elevation).

1. Install (user-level, no admin):

irm https://raw.githubusercontent.com/Ruby570bocadito/bluetardigrade/main/install.ps1 | iex

To build the Rust ETW sensor too, pass -WithSensor:

& ([scriptblock]::Create((irm https://raw.githubusercontent.com/Ruby570bocadito/bluetardigrade/main/install.ps1))) -WithSensor

2. Open a new terminal so the PATH change applies, and check it:

sf-engine version

3. Install a sensor once: the Rust ETW sensor with sf-etw -Install (one UAC prompt), or Sysmon with sf-sensor -SetupSysmon.

4. Start everything. The browser opens at http://localhost:3000 (when another program holds that port, the console moves to the next free one and remembers it):

sf-start      # engine, console, AI hub and the sensor service
sf-status     # what is running
sf-stop       # stops it all (-KeepSensor keeps the sensor capturing)

5. Verify the pipeline and fire a harmless detection (the download target is a closed local port, so nothing is fetched):

sf-engine doctor
certutil -urlcache -f http://127.0.0.1:9/prueba.txt "$env:TEMP\prueba.txt"

The console raises "Descarga con certutil o bitsadmin" (MITRE T1105) within seconds.

Linux, macOS or Docker (engine + collectors)

The source path needs Go 1.26.10 or newer (https://go.dev/dl/) and make; Docker needs neither.

git clone https://github.com/Ruby570bocadito/bluetardigrade.git

./bin/engine run -i                       # interactive terminal workspace

Notifications

Every alert that passes a channel's minimum severity reaches that channel, without ever slowing detection down (one bounded queue per channel, three attempts, every outcome counted on /api/stats and /metrics).

Channel What arrives You need
ntfy A push on the phone: [CRITICAL] rule @ host as the title, the severity as the priority (critical rings through do not disturb), a tap opens the alert The ntfy app and a topic on ntfy.sh or on your own server
Email The alert line, its link and the full alert as JSON (the mailbox doubles as a record) An SMTP relay (StartTLS by default)
Telegram The alert line and its link A bot from BotFather and the chat id
Slack The alert line and its link An incoming webhook

From the console (administrators, engine started with -api-write — sf-start does both): Ajustes → Avisos externos, add a channel, choose its minimum severity, fill in the console address so every message links to its alert, Guardar avisos, then Enviar prueba. Secrets are write-only: the console shows «guardado» and never reads them back.

Phone push in three steps:

  1. Install ntfy on the phone (Android or iPhone) and subscribe to a hard-to-guess topic, e.g. soc-acme-7f3k.
  2. In Ajustes → Avisos externos, add an ntfy channel with the server (https://ntfy.sh, or yours) and that topic, minimum severity Alta.
  3. Enviar prueba: the phone rings. From now on, so does every high or critical alert.

Or as a file — tools\config\notify.yaml, the same one the console writes (full example):

console_url: https://soc.acme.local          # every message links to its alert
channels:
  - type: ntfy
    name: guardia-movil
    min_severity: high
    url: https://ntfy.acme.local             # or https://ntfy.sh
    topic: soc-acme-7f3k
    token_env: SF_NTFY_TOKEN                 # only if the server has access control
  - type: email
    name: soc-correo
    min_severity: medium
    server: smtp.acme.local:587
    from: bluetardigrade@acme.local
    to: [soc@acme.local]
    username_env: SF_SMTP_USER
    password_env: SF_SMTP_PASSWORD
  - type: telegram
    name: guardia-telegram
    min_severity: critical
    token_env: SF_TELEGRAM_TOKEN
    chat_id: "-1001234567890"

On your phone

https://<your console>/movil is the console for whoever is on call, and it installs as an app (home-screen icon, full screen, opens straight on the alerts).

The badges on the tabs count critical alerts, open incidents and silent machines. A viewer sees the cards without the buttons; every decision is signed with the session's account, exactly as on the desktop.

Connecting a phone

A phone reaches the console over the network, and browsers only install apps from HTTPS. Publish it inside the company network or its VPN — never to the internet:

  1. Accounts with two-step sign-in for everyone who will use a phone:

    sf-console -AddUser ana -Role analyst
sf-console -RequireMfa admin,analyst

  2. Let the console answer to the name the phones use, and only from the VPN. Add it to the console's allowed hosts and open the port in the server firewall to the VPN range only (no port forwarding on the router):

    # then sf-stop and sf-start from a new terminal
[Environment]::SetEnvironmentVariable('CONSOLE_ALLOWED_HOSTS', 'soc.acme.local', 'User')
New-NetFirewallRule -DisplayName 'bluetardigrade console (VPN)' -Direction Inbound `
  -Protocol TCP -LocalPort 443 -RemoteAddress 10.8.0.0/16 -Action Allow

  3. Put HTTPS in front with a certificate the phones trust (your company CA). For example with Caddy on the same server:

    soc.acme.local {
    tls C:/certs/soc.acme.local.crt C:/certs/soc.acme.local.key
    reverse_proxy 127.0.0.1:3000
}

    Caddy sends X-Forwarded-Proto: https, so the console marks its session cookie Secure and sends HSTS. IIS with URL Rewrite or nginx work the same way.

  4. On the phone (connected to the VPN), open https://soc.acme.local/movil and sign in. Then:

    • Android (Chrome): menu ⋮ → Instalar aplicación.
    • iPhone (Safari): Share → Añadir a pantalla de inicio.

Sessions on the phone follow the desktop rules: they expire when idle and after 12 hours, end on sign-out, and end on the server when the account changes. Pairing a phone by QR code with per-device sessions is on the roadmap. Details: The console on a phone.

Security model

Layer Control
Ingest Shared token or per-sensor identities bound to their hosts; events for other hosts are refused and counted
Transport Native TLS on both listeners; the sensor trusts only the CA you give it
API Bearer token; listens on loopback by default
Console Sign-in page and expiring sessions; per-analyst accounts (viewer / analyst / admin) or Active Directory accounts by group; optional or per-role TOTP; host groups that limit what an account sees; every write and sign-in audited
AI hub HUB_ACCESS_TOKEN per socket, Origin allowlist and shared rate limits
Response kill_process needs an arm flag, a response token and per-operator credentials; protected processes are refused; every attempt audited
Evidence Stored events are append-only: a second copy of an event id cannot rewrite the first
Privacy Reads of a user's directory record are audited; personal audit tables expire with the store retention
Supply chain SHA-pinned GitHub Actions, minimal permissions, Sigstore release attestations

Report vulnerabilities privately: SECURITY.md.

Roadmap

  • Before 1.0: a 24–48 h soak test with the sensor as a service, laptop suspend, long engine outages and a week of CPU and memory on real Windows hosts (checklist).
  • Next:
    • extended response, opt-in at install: isolate a host, quarantine a file, signed and audited orders to the sensor, one- or two-person approval;
    • pairing a phone by QR code, with per-device sessions revocable from the console;
    • a reviewed SigmaHQ pack, a rule editor and YARA management in the console;
    • continuous anti-phishing (IMAP mailbox, SPF/DKIM/DMARC, look-alike domains, QR codes).
  • Later: lite and full editions, a signed plugin catalogue, explainable ML triage, and many engines under one master for large fleets.

The full plan is in docs/ROADMAP.md and TODO.md.
